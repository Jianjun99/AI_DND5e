# 项目评估与下一轮开发建议

评估日期：2026-09-30。评估对象：工作区中的 `package.json` 版本 1.9.8。

本文是评估和候选任务规格。除“已观察 / 已复现”部分外，所有设计均为建议，尚未实现；后续 agent 不得将建议当成已有功能。

后续整理说明：本评估保留检查当时的观察，部分文档漂移已在交接整理中校正；游戏 bug 尚未修复。现在的执行规格与任务状态以 [tasks/README.md](../tasks/README.md) 和各 task 文件为准。新 agent 从 [START_HERE.md](../START_HERE.md) 进入，项目拥有者使用 [交接指南](AGENT_HANDOFF.md)。

用户目标：做一个可以独自玩的、可扩展的 D&D 游戏，以 AI 增强游戏性。用户明确指出当前主要问题是：“功能已经很多，但体验不顺、不知道该玩什么。”

## 1. 建议先完成的目标

下一轮开发以“第一次冒险能顺畅完成，并且回城后知道为什么继续”为目标。

现有规则、战斗、装备、城镇、主线、同伴、程序地牢、每周挑战已经足以支撑这一轮。最有价值的工作是把这些功能组织成玩家能理解的连续体验。

优先顺序：

1. 修复影响操作确定感的入口、状态覆盖、旁白持久化、重复结算问题。
2. 串起首页 → 出发准备 → 地牢目标 → 结算 → 下一目标。
3. 给第一次游玩的玩家默认选择和情境提示。
4. 在这条流程里加入有真实依据的 AI 建议、角色记忆与一个分支遭遇。
5. 用这一个遭遇验证扩展协议，再扩写模组。

不建议把下一轮的主要预算投入新怪物、新特长、新货币或等级上限；它们不能直接解决本次反馈。

## 3. 已复现的问题

| 问题 | 实际观察 | 位置与原因 | 建议优先级 |
|---|---|---|---|
| 准备页选择被忽略 | 在 `#/play/new?char=...` 选择 howling-hills、hard、solo，实际开局为 crypt、normal、Bram | `public/js/views/play.js:82` 传 options 对象，而 `public/js/api.js:28` 接收四个位置参数；对象被当成 bringAlly | P0 |
| 慢描述请求覆盖移动 | 初始 (4,4)，移动响应为 (5,4)，700ms 的 describe 请求完成后存档回到 (4,4) | `server/routes/game.js:175` 每个请求读取独立快照，describe 等 AI 后在 `:608` 写回旧状态；前端 `play.js:621` 的描述请求可独立于 act 发出 | P0 |
| AI 旁白没有保存 | 开局响应含 mock 旁白，随后 GET 同一局不含该旁白 | `server/routes/game.js:152` 保存先于 `:153` 旁白；普通动作 `:608–609` 同样如此，narrate 只修改当前对象 | P0 |
| 同一局重复结算 | 同一个 retreat 存档结算两次，delvesCompleted 从 1 变 2 | `server/routes/city.js:560` 没有整局结算去重，`:687` 每次增加次数；个人主线推进的幂等不能代替整局结算幂等 | P0 |

准备页问题的范围是这个独立入口；区域地图出发使用四个位置参数，不能将它描述成“所有开局都坏了”。

慢描述复现使用隔离存档与本地 mock：describe 请求中的模型等待 700ms，120ms 后发出普通移动；移动完成后等待 describe，重新 GET 存档。普通移动确实成功，随后被较早请求的快照覆盖。

旁白持久化复现使用标记文本 `REVIEW_MOCK_NARRATION`，比较 POST start 的返回日志和随后 GET 的日志。是否出现标记不依赖 RNG。

### 与这些问题相关的代码观察

- `public/js/views/play/panels.js:238` 每次打开结算界面都会发送 sync-delve，且 `.catch(() => {})` 吞掉失败；界面同时允许马上离开。奖励同步缺少明确完成状态。
- sync-delve 会把地牢快照的背包、金币、XP 写回档案。重复结算旧局可能覆盖之后的角色变化；此次只动态验证了次数重复，其他覆盖后果应补独立用例。
- `play.js:722` 用 busy 丢弃后续输入，而动作 HTTP 响应要等待旁白。模型较慢时玩家会感到点击不生效；本次没有用真实模型量化延迟。
- `public/js/dice.js:23` 在客户端掷骰；锁箱/拆陷阱提交 rollTotal，路遇也由客户端选择事件和判定结果。这是当前实现与 AGENTS“引擎唯一裁判”之间的实际偏差。
- 前端 `isAreaCleared` 的“没有活怪物”与引擎 `checkVictory` 的“目标完成且回到营地”是两种条件。提示应区别“区域安全”“目标完成”“已经结算”。

## 4. 玩家体验：把功能串成一场冒险

### 首页：让玩家继续一个明确目标

现在首页主要是英雄卡、模组管理和备份。有存档时，继续按钮是一个小剑图标；卡片没有回顾当前目标。

建议主卡显示：

> 继续 Review Hero 的冒险  
> 第一幕：圣物。上次停在墓穴入口，准备探索深处。  
> 主按钮：继续冒险  
> 次按钮：查看冒险计划

没有活动存档时，主按钮变为“准备下一次冒险”，并说明建议去哪、为什么。新玩家可选“推荐英雄开始”或“自定义英雄”。模组导入、备份放在清楚可见的管理入口里。

### 出发准备：先建议，再允许调整

区域地图已经有主线横幅与标记，但默认选中城镇，地图节点、城市系统、难度和同伴需要玩家自己拼接。

建议在横幅附近加一张行动卡：

> 当前目标：带回圣物，开启第二幕。  
> 推荐目的地：沉没墓穴。  
> 准备：生命已恢复；携带 2 瓶治疗药；可以选一位同伴。  
> 主按钮：前往墓穴准备  
> 次按钮：查看其他冒险

建议来自服务端的真实状态。按钮先进入确认准备的界面，不自动花钱、招募或出发。地图、难度、同伴在一个共同的准备流程里确认。

每周挑战、无尽深渊保留明确入口，作为完成基础冒险后的另一种目标。不要把它们与首次主线出发都呈现成同等推荐项。

### 地牢：目标要能逐步变化

现有地图顶栏、hover 提示和右侧任务卡已经解释了移动及整体目标。缺的是“这个阶段接下来做什么”。

- 刚进入：探索通道；与附近 NPC 交谈；检查附近可见对象。
- 战斗：清楚显示行动、附赠行动、移动还剩什么；动作不可用时说明原因。
- 拿到圣物：主提示切换为“返回营地”，显示已知出口方向。
- 目标满足、尚未回营地：解释还剩返回这一件事。
- 需要提示时：只提供当前发现区域和合法动作中的线索，不暴露未知房间或隐藏陷阱。

当前行为解析主要匹配英文关键词，中文输入没有相应规则匹配；界面又混用中英文。应先选定默认语言，并让目标、按钮、错误提示和自由输入支持保持一致。多语言大改可晚于这一条主要流程。

在手机普通模式的首屏，地图与日志占据主要空间，行动区位于其后；顶栏目标也会被截断。建议首先保证“当前目标摘要 / 常用行动 / 展开详情”随手可达，并检查它们在普通模式与沉浸模式的表现。

### 结算：告诉玩家发生了什么，以及接下来为什么走

现有结算偏向统计伤害、金币、轮数和击杀。建议把上半部分改为：

- 本次目标：成功 / 撤退 / 失败，原因清楚。
- 真正新增的东西：奖励、装备、等级变化、同伴变化。
- 世界进度：例如圣物已带回，第二幕的地窟钥匙有了线索。
- 下一目标：主线继续 / 补给 / 队友任务中的一个明确建议。

伤害统计放在详情。结算成功后才把奖励描述为已保存，并启用返回入口；失败提供重试。重新打开详情不能重复支付奖励或覆盖角色。

### 快速开始与小教学

完整七步角色创建保留给喜欢 build 的玩家。推荐英雄使用服务端 `buildCharacter` 和现有规则生成；客户端只选择 presetId，不复制属性与装备数值表。

第一版可提供两个易理解的预设，先让玩家体验移动、交互、一次战斗、一次取舍和回城。需要专门教学地图时，目标控制在约 10–15 分钟，复用现有对象与渲染器；这是设计目标，尚未做实测。

推荐把“第一次完整体验”与“资深玩家所有功能”设计为同一个游戏中的不同展开程度。这个方法参考 [NN/G 对渐进展示的说明](https://www.nngroup.com/articles/progressive-disclosure/)；具体入口分组是基于本项目界面的建议。

## 5. AI：先帮助玩家理解，再增加真实选择

### 第一优先：当前情境下的建议

AI 读取引擎生成的可用动作、当前可见信息和已确认目标，写一两句解释。例如：

> 你已完成本层目标。先回营地把成果带出去；继续探索会增加风险。

或解释当前战斗为什么还能移动、为什么这个法术不可用。输出可以引用 actionId 并显示为按钮，点击后重新由引擎检查。建议结果过期时要重新验证。

无需每走一格都问模型。首次房间进入、重要选择、战斗结束、目标变化和玩家主动求助是更有价值的触发点。没有模型时，确定性建议仍然存在。

### 第二优先：角色与冒险记忆

现在 npcChat 保留当前地牢的一小段对话，recap 主要从近期日志生成；同伴个人任务是忠诚门槛加杀怪计数。

建议把关键事实单独保存：救过谁、答应过什么、选择了哪条路线、某同伴为何信任玩家、任务最终结果。由引擎写入结构化事实，AI 据此表达态度；AI 生成的总结不能反过来成为世界事实。

开始时只给一个同伴或 NPC 做两三个记忆点。比如同伴曾因玩家冒险救援而增加信任，下次进城能提起这件真实发生的事。先验证这种体验是否有趣，再推广。

### 第三优先：一个有两种解法的遭遇

示例：通往遗迹的门被一位守卫挡住。

- 可以战斗；
- 可以用已经找到的凭证说服；
- 若角色具备合适能力，可以尝试一次受引擎约束的检定。

结果影响之后的线索或 NPC 态度，而不是三个按钮给出同一结果。第一版不需要完整阵营系统；一两个持久化事实足够。

这里可以参考 [Ink 的变量、条件选项与分支写法](https://github.com/inkle/ink/blob/master/Documentation/WritingWithInk.md)。建议借用这种组织方式，在现有 JSON 模组协议中实现最小版本；没有必要先引入一个新的叙事运行时。

### 自由输入的后续路径

当前 `referee.js` 是关键词 → 固定动作；未匹配文本交给 `freeformFlavor`，后者明确不改变游戏世界。因此“写得更像主持人”不会自动产生更自由的玩法。

后续可以扩成：

```mermaid
flowchart LR
  T[玩家自由输入] --> P[关键词解析或 AI 意图提案]
  P --> V[服务端验证目标、距离、资源、动作权限]
  V --> E[现有引擎检定与状态变化]
  E --> F[保存事实与事件]
  F --> N[AI 解释结果]
```

AI 只能建议允许的动作种类和真实 targetId，不决定骰点、奖励、DC 或最终成功。先覆盖观察、交谈和已有动作，再考虑环境组合；不以“任意想法都能实现”为第一版目标。

## 6. 架构建议：补契约，保持当前部署形式

### A. 状态修改入口与慢 AI 工作分离

现在同步 JSON 文件写入本身有临时文件 + rename；主要问题出在多个异步请求持有不同旧快照，而非单纯文件写入速度。

建议：

- 对同一存档的读改写形成受控执行顺序，提交机械结果时递增 revision。
- 服务端完成机械操作和持久化后，及时返回事件与默认文案。
- 描述、头像、旁白只提交它们自己的缓存/日志结果，不能写回整份旧 game state。
- 异步结果用 actionId/eventId 关联；写入时读取最新状态并只追加自己的结果，按需要检查 revision 或上下文是否仍有效。
- 前端对过期响应做检查，不能让较慢的辅助响应替换更晚的游戏状态。
- 角色档案修改与地牢结算也要纳入清楚的状态所有权规则。

第一步不需要迁移数据库、引入消息队列或全量事件溯源。也不要用“生成旁白后再保存一次旧 state”修旁白丢失，这会放大已经复现的覆盖问题。

### B. 结算收据与角色快照的约定

给一次结束的地牢分配稳定结算标识；角色档案记录已处理标识和收据。再次请求返回同一收据，不重复加次数、排行、奖励，也不再次同步旧背包。

同时检查地牢归属与可结算状态。由于 JSON 档案和地牢是两份文件，明确哪个记录是重复处理的依据，以及中途写失败后如何恢复；不依赖两个写入永远一起成功。

当前同一英雄能存在多份地牢存档，城镇改动还会向存档同步。需要写清楚：它们是可独立继续的快照，还是共享一个持续英雄？旧局结算对后来升级、购买、锻造有什么权限？先把语义定下来，再统一实现，避免继续增加临时 write-through 分支。

### C. 服务端提供目标和合法行动

可在既有 city info 与 game payload 中增加 guidance，而不是另做一套客户端判断规则：

```json
{
  "guidance": {
    "phase": "prepare",
    "objective": "取回圣物并返回营地",
    "primary": {
      "id": "prepare_crypt",
      "label": "前往墓穴准备",
      "reason": "这是当前主线的下一步",
      "mapId": "crypt"
    },
    "alternatives": []
  }
}
```

这是协议示意，不是现有字段。它要复用 campaign、levelUpInfo、可见信息与引擎状态；主线推荐、实际关卡胜利条件和城镇服务不要各自建立一份重复事实表。

### D. 明确骰子裁决归属

把锁箱、拆陷阱和路遇改为客户端提交意图，服务端掷骰并返回 natural/modifier/total/DC/outcome，客户端播放结果。每周 seeded RNG 也沿同一条流走。

这项工作是落实已有 AGENTS 约束，有助于重放、存档续接和解释判定；不需要因为这个个人项目引入复杂反作弊系统。

### E. 数据驱动扩展到“冒险”，并完善验证

模组现在主要提供地图、怪物、装备，主线与同伴任务仍在核心代码中。真正能扩展玩法，需要一个小型 scene/choice/condition/effect 协议：

- 条件：已确认的故事事实、技能/道具要求、关系阈值；
- 行动：显示合法选择，调用引擎已有检定；
- 后果：允许的标志变化、奖励、关系变化，支付可去重；
- 叙事：默认文案 + AI 可以使用的事实；
- 完成：引擎认可的目标条件。

先只服务一个分支遭遇。物理地图与自由输入都引用同一遭遇定义，避免写两套结果。

`content.js` 已做基础字段检查，但还需检查声明尺寸与 rows 的一致性、坐标边界、玩家出生和出口、monster/item/npc/stairs 引用、victory 类型与目标存在性，按需要增加静态可达性检查。错误应带 pack、文件与字段路径。

当前首页能观察到 howling-hills 与核心 dire_wolf 重名的 warning；内容检查应帮助作者区分“加载成功”“部分内容被忽略”“内容不可玩”。

### 本轮保留的决策

保持单 Node 进程、原生前端、JSON 本地存档和可选模型；保持引擎唯一裁判和服务端唯一事实来源；按照 AGENTS 不物理拆分 engine.js、不引入 React/Vue/打包器。

上述职责可以先通过少量明确的服务函数、类型和协议表达。拆大文件不应成为完成玩家体验目标的前置条件。

- MODDING 的“无地图间旅行”“emoji token”限制与现有楼梯和 3D 手办不一致。
- README 的规则等级说明及地图列表存在旧内容和重复行。

这会让下一位 agent 冷启动时花时间辨认真伪，甚至重复实现完成过的任务。

### 建议最小资料结构

| 资料 | 负责什么 | 维护方式 |
|---|---|---|
| AGENTS.md | 硬约束、验证、协作边界 | 保持规则正本，避免重复维护 |
| PROJECT_STATE.md | 当前版本、真实在做的任务、已知问题、下一目标 | 保持简短，将长发布历史移出 |
| 一页游戏设计说明 | 玩家幻想、主要循环、推荐玩家路径、AI 的职责 | 新功能先说明对哪段体验有帮助 |
| ARCHITECTURE.md + 关键决定记录 | 状态所有权、AI 慢响应、结算、扩展协议 | 记录为什么这样做与何时重新评估 |
| tasks/ 的任务规格 | 目标、文件范围、排除范围、依赖、验收、存档影响 | 任务状态放开头；验证后更新 |
| API / event / save 的类型和例子 | agent 能准确修改的接口 | 优先补 StartGameOptions、Action、Event、Guidance、SettlementReceipt 的 JSDoc |

已经有 JSDoc + tsc，不需要换 TypeScript 技术栈。但部分 ctx/action/API 参数是 any 或推断过宽，准备页传错参数仍能全绿，说明关键边界类型有补充价值。

### 需要补的验证场景

现有引擎不变量和浏览器布局测试继续保留。增加能够覆盖实际旅程的检查：

1. 通过各出发入口选择地图/难度/同伴，响应必须与选择一致。
2. 延迟 mock LLM 描述与普通动作并发，较晚位置/资源不能回滚，辅助结果也不能覆盖前端新状态。
3. 生成的旁白在刷新/重连后仍可读，并且不重复追加。
4. 同一局结算两次，次数、金币、XP、背包、每周排行和主线日志均不重复变化。
5. 重新打开旧结算后，之后的城镇购买与升级仍被保留。
6. 结算请求失败时界面不能说奖励已保存，重试后只处理一次。
7. 取到目标后提示转为返回；回城后提示转为新一幕或其他实际目标。
8. AI 不可用时仍有明确目标和操作；未知输入应说明未产生规则效果并提供可用行动。

这些测试验证玩家可感知的行为，不锁定 RNG 具体值。e2e 按条件等最终状态；测试 runner 要真实计数失败。

体验评估还需要实际试玩：让自己或一两位没读代码的人走一次，从进入首页到回城。记录在哪里停住、为什么按按钮、误解了什么。单靠“没有横向溢出”“所有 API 200”不能证明知道下一步。

## 8. 建议任务队列与验收

以下为候选任务，可按单任务交给其他 agent。每项实施后按 AGENTS 完整 verify；任何数值表变化另跑 balance-sim 并报告结果。

### T1 — 准备入口与接口类型

- 目标：各入口的地图、难度、同伴设置真实生效。
- 范围：api.js、play.js、overworld.js、weekly 入口与相关测试。
- 选择一种统一调用形式；补显式 StartGameOptions 与调用端类型。
- 验收：非默认地图 + hard + solo，以及至少一位非默认同伴，都从 UI 正确进入；区域地图和每周入口仍能开始。
- 不扩职业、不改数值。

### T2 — 状态更新与 AI 结果持久化

- 目标：慢描述/头像/旁白不覆盖玩家行为，结果能正确保存。
- 范围：game routes、store 的受控修改入口、play.js 的辅助响应应用、LLM mock 测试。
- 先实现最小状态顺序与辅助结果合并，不进行全引擎物理拆分。
- 验收：并发请求不回滚位置/HP/资源；刷新后旁白存在；旧响应不能覆盖前端新 revision；模型故障有默认文案且操作可完成。

### T3 — 结束冒险与幂等结算

- 目标：一次冒险只结算一次，回城看到真实最新档案。
- 范围：city sync-delve、结算界面、角色/存档版本契约、迁移 fixture。
- 验收：两次结算相同收据、统计与奖励只变一次；归属/终态检查；同步失败可重试；旧详情不覆盖后来购买/升级。
- 先定义多存档角色的同步语义。

### T4 — 从首页到下一目标的引导

- 目标：玩家每个阶段都能看出“当前目标、下一步、为什么”。
- 范围：复用 campaign 的服务端 guidance；home、overworld、play、summary。
- 第一版用确定性模板，完全不依赖 LLM。
- 验收：新英雄能看出推荐主线出发；目标拿到后提示回营地；结算后看出下一幕；主动作在桌面/手机普通及沉浸模式可达。
- 不复制 XP/战斗/胜利数据表，不暴露未发现地点。

### T5 — 快速开始与一次完整体验

- 目标：玩家可以先玩再理解完整创建选项。
- 范围：两个服务端英雄预设、入口文案、少量按需教学；如确有必要再做短教学地图。
- 验收：无需七步创建即可进入可玩冒险；教程提示可跳过；原自定义创建保留；试玩能完成出发 → 行动 → 目标 → 回城。
- 在这一阶段记录首次操作/卡点的实测，不先建设遥测平台。

### T6 — 一个有记忆与后果的 AI 遭遇

- 前提：T2、T3、T4 稳定。
- 目标：让 AI 帮助玩家理解选择，并让 NPC 在之后记得这次决定。
- 范围：一个 JSON 遭遇、两种可执行解法、少量引擎事实、一个 NPC/同伴的后续反应、内容校验。
- 验收：两条路线有不同且持久化的后果；断开 LLM 仍可完成；AI 不授予物品/修改检定；重新读档后 NPC 反应与真实选择一致。
- 不先做通用开放世界生成器、完整阵营模拟或无限自由动作。

文档整理可在 T1 前或同时完成，但新路线图不应再次把已完成的 PWA、特长和存档版本化列成待实现。

## 9. 怎样判断这一轮值得继续

建议先用下列体验结果验收，而不是功能数：

- 玩家进入后能很快说出自己要去哪、为什么。
- 关键按钮的选择和结果一致，失败/等待有反馈。
- AI 慢、断开、刷新均不造成机械状态丢失。
- 回城结算能看到本次收获和下一步。
- 同一个小遭遇能采用两种方法完成，并且之后有不同回应。

前四项改善的是现有瓶颈；第五项才开始验证“AI 增强单人 D&D”最有潜力的部分。
