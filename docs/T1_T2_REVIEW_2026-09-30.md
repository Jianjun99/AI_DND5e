## P1：旧轮询响应能回退画面

定位：`public/js/views/play.js`，`pollTimer`（复核时 1428–1436 行）。

轮询用 `rev !== 当前 rev` 判断是否更新，随后直接 `game = data.state`。这允许较低版本覆盖较高版本，绕过了 `adoptState`。检查 busy 只发生在发请求之前，不能防止等待期间的动作。

隔离真实浏览器复现：

1. 正常加载 crypt 存档；保存实际轮询回调，手动触发它以控制顺序。
2. GET 已收到 rev=1 的服务端响应；在浏览器 fetch 包装层暂缓交给页面，不改响应内容。
3. 用 ArrowRight 发起正常移动，等页面采用 rev=3。
4. 释放旧 GET 响应并等待轮询完成。

| 时点 | 页面 rev | 玩家格子 |
|---|---|---|
| 移动前 | 1 | (4,4) |
| 正常移动完成 | 3 | (5,4) |
| 旧轮询返回后 | 1 | (4,4) |
| 最后重新 GET 服务端 | 3 | (5,4) |

这是画面状态回退，服务器存档没有丢失移动。下一次轮询可能恢复，但期间页面会用旧状态判断动作、资源和结束条件。修复所有当前页面的状态采纳入口，轮询与升级后的 GET 也应遵守版本及存档身份检查。

## P2：并发 NPC 对话会丢失已经保存的记忆

定位：`server/routes/game.js` 的 chat pending apply（复核时 550–556 行）；`server/game/dm.js` 的 `npcChat`。

`latest.npcChat[npcId] = state.npcChat[npcId]` 将等待前快照中的整段历史写回，即使整个存档已经重读，也会覆盖这个字段内的并发新内容。

隔离真实路由复现（不使用玩家的模型服务）：

1. 向附近 NPC bram 发送 `review-chat-A`，mock 接收后扣住回复。
2. 同一存档、同一 NPC 发送 `review-chat-B`，立即回复并确认 GET 历史包含 B 的问答。
3. 释放 A 的回复，重新 GET。

最终 `npcChat.bram` 只有 A 的问答，B 的问答消失；可见 log 却仍有 A、B 两条回复。这会让后续模型忘记已经发生的对话。单页面 act 的 busy 挡住多数连续点击，但多标签页/并发 API 仍会触发；服务端写入契约应独立保证正确。

建议以动作 ID 关联本次问答，向最新历史合并这个动作的新增内容，规定乱序完成时的排列方式。保留历史长度上限；模型等待继续在锁外。无需把整局锁持有到模型回复。

## 需要纠正的一处测试覆盖

`tests/integration/state-and-ai.test.mjs` 的普通动作旁白用例，在 `startDelve` 之前就 enqueue 了 `MOCK ACTION NARRATION`，标记会被开局旁白消费；移动后检查完整 log 仍含这个标记，并不能单独证明移动旁白已保存。补修时应在开局完成后才安排动作的独立回复，并断言其 aid 与开局不同、动作前不存在、动作后 GET 恰好一次。这是回归测试的缺口，不是另一个已复现的游戏旁白丢失问题。

## T3 的当前复现与实现注意

同一 retreat 存档连续两次 `sync-delve`，`delvesCompleted` 从 1 变成 2，T3 原问题仍存在，属于 T3 范围。

- 沿用 T2 的同步机械提交与最新状态合并契约，别重新保存等待前整份存档。
- 结算标识必须稳定，不能拿不断增长的 `rev` 当去重键。慢旁白会继续增加 rev，但不能因此再发一次奖励。
- 明确角色档案与地牢两份文件的写入顺序、权威收据和失败重试恢复；别只在客户端设“已结算”。
- 重复结算要返回同一收据，并保留结算后的购买、装备和升级；测试次数、金币、XP、背包、weekly 和主线。
- 结算 UI 要显示保存中/成功/失败，失败可重试。不要提前改 T4 的目标导航。
