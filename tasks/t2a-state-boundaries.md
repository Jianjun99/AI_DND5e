## 问题与代码入口

1. `public/js/views/play.js` 的 pollTimer 在旧 GET 返回后直接替换 game，导致页面 rev=3、(5,4) 回到 rev=1、(4,4)，服务端仍是新状态。`adoptState` 本身已有版本检查，但轮询没有使用；升级后 GET 也直接赋值。
2. `server/routes/game.js` chat pending apply 从快照整段替换同 NPC 历史。A 请求扣住、B 先完成、A 再返回，最终 npcChat 丢失 B 的问答；log 仍含两条回复。读 `server/game/dm.js` 的 npcChat，理解它如何修改提示词快照。

现有测试：`tests/integration/state-and-ai.test.mjs`、CDP 套件与 `_cdp-helpers.mjs`。复用现有测试结构，优先扩展既有套件。

同一套件的普通动作旁白用例把动作标记放在 startDelve 之前，实际由开局消费；应改为开局完成后安排独立动作回复，避免只是重复证明开局旁白存在。

## 范围与实现约定

- 统一异步响应的整体状态采纳：当前存档身份匹配，版本不低于已展示版本，当前页面仍有效时才更新。检查轮询、升级后的 GET 与已有动作/辅助响应；初次加载新存档需有明确初始化边界。
- NPC 历史在最新存档上合并本次动作的问答，不从提示词快照整段覆盖。用既有 actionId/aid 或同等稳定标识关联，规定并发乱序回复的历史排列方式和长度上限。
- 模型等待仍在锁外；机械状态只由引擎提交；不能靠整局长锁或客户端 busy 解决服务端并发。
- 不改变 API 既有主要响应形状，不引入框架、SSE、消息队列，不实施 T3。

## 验收标准

- [ ] 在真实浏览器扣住旧轮询 GET，完成正常移动再释放 GET；页面最终版本、位置及资源保持新值，服务端亦保持新值。
- [ ] 后续正常较新轮询可采用，辅助描述/头像仍能显示。
- [ ] 较旧存档响应不能误入刚切换的存档页面；旧档无 rev/关联字段仍可用。
- [ ] 同存档同 NPC 两个并发对话、逆序释放回复后，GET 历史与可见日志保留两次问答且没有错误配对；后续对话提示词仍包含应保留的历史。
- [ ] 不同 NPC/不同存档的历史不串；记录去重、排序与截断规则，不依赖随机骰值或固定 sleep 安排完成顺序。
- [ ] 普通动作旁白用例的标记在动作前不存在，动作后带独立于开局的 aid；POST/GET 恰好一次，不能被开局旁白代替。

## 交接结果

- 完成范围（2026-09-30）：
  - **P1 状态采纳统一（play.js）**：`adoptState` 升级为唯一天 gate——先比存档身份（
    `next.id !== game.id` 拒绝，旧档响应不能误入刚切换的存档页面），再比 rev（低于已展示
    版本拒绝，等于允许——同档新 GET 是当前态）；轮询从"`rev !==` 就直接赋值"改为
    `adoptState(data.state) && update()`；升级弹窗后的 GET 同样走 `adoptState`。新增
    `viewToken`（每次 playView 挂载 +1）与 `viewAlive`（cleanup 置 false）：初始化 GET 返回
    时若已有更新的视图挂载则放弃（明确的初始化边界），轮询回调在发出前与返回后都检查
    `viewAlive`——视图结束后在途的 GET 不能再写 `game`。
  - **P2 NPC 记忆合并（routes/game.js chat apply）**：不再把提示词快照的整段
    `npcChat[npcId]` 写回最新档；改为按本次动作的 `actionId` 追加这一对问答
    （`{role:'user',aid}` + `{role:'assistant',aid}`），`hist.some(m => m.aid === actionId)`
    去重防重复追加；乱序完成按完成顺序排列（先完成先落库）；24 条上限与 dm.npcChat 的
    截断一致；`chatReply` 为 null（无 NPC 定义）时不追加。模型等待仍在锁外。
  - **测试覆盖缺口修正 + 回归**（state-and-ai 套件，47→47 项断言内含新增用例）：
    - 普通动作旁白用例重写：标记在 `startDelve` 完成后才入队——断言动作前标记不存在、
      动作后恰好一次且 `aid` 不同于开局旁白的 aid、POST 与 GET 一致。

      GET 断言两次问答各恰好一次、完成顺序排列、问答正确配对、log 仍含两条回复；
      后续第三次对话的提示词（mock 捕获请求体）仍包含 A、B 的问答。
    - mock LLM 增加请求体捕获（`bodies`）用于提示词断言。
